## SYSTEM GROUND RULES (NON-NEGOTIABLE DESIGN PRINCIPLES)
1. ZERO PRESENTATION REGRESSIONS: Do not alter, edit, or degrade the existing visual component files, 55 reusable UI components, Tailwind frameworks, spacing grids, or color palettes unless the user explicitly requests a visual change.
2. IMMUTABLE NETWORK PERIMETERS: Enforce Helmet Content Security Policies, precise cross-origin CORS limits, and `TRUST_PROXY_HOPS` from the environment (default `1`; the documented agency topology uses `2`). Audit identifiers use keyed HMAC-SHA256 via `AUDIT_ID_HMAC_KEY`, not an unkeyed salted hash.
3. LOCAL VAULT LOCKING: The device-local IndexedDB vault encrypts records with AES-GCM; PBKDF2-SHA256 (600,000 iterations) derives its in-memory key. `lockNow()` drops the key reference and resets decrypted workspace state. Sign-out clears the React Query cache and locks the vault; Clerk account changes do the same. Ciphertext remains on the device. Do not claim guaranteed physical memory zeroization or certified agency compliance.

## 2. CHRONOLOGICAL FOLDER ROUTING & DAILY PAGE INDEXING
The packet is rebuilt from the current daily report and matching phase schedule. There is no persisted shared page counter and no application-defined page cap; page references are derived from the generated packet order.
* PAGE 1: Reporting for Duty (Form U-10.191) is always first. The daily report uses the active phase folder's assignment metadata. Cruiser ID remains editable plain text. Shotgun training is represented by "Y" or "N"; selecting "N" marks Resource/Equipment Usage not applicable for that report.
* SUBSTATION ORIENTATION (U-10.181): Required once on the first scheduled workday of a phase when no matching orientation record exists. When present, the current orientation form occupies two sheets beginning at Page 2; it is not a single-page hook.
* RUN AND SUMMARY ORDER: Runs are ordered by start time. Required supplemental forms and generated narrative continuations follow their run. The daily performance summary and any continuation sheets are last. A new daily report creates a new packet projection beginning at Page 1; this does not delete saved reports or encrypted local records.
* PAGE REFERENCES: `W#D#P#` coordinates derive from the scheduled training week/day and the packet page index. They are not a separately persisted counter.
* PATROLVIEW STATUS: A protected same-origin event-ID prefill route exists, but no live feed is configured and this is not the desired incident-number workflow. The required behavior is to query only after the FTO enters an incident number, then match returned unit data against the Reporting for Duty `cruiserId`. Apply values only for exactly one exact unit match; absent or ambiguous matches stay manual. All prefilled values remain editable, and FTO corrections must not be overwritten. The user will provide a PatrolView run-page example before the unit/metric response mapping is implemented. Do not enable live lookups or infer per-officer activity totals before that mapping is reviewed. The existing route still requires a verified Clerk session and `PATROLVIEW_ALLOWED_CLERK_USER_IDS`; its current event-ID adapter also requires `PATROLVIEW_EVENT_LOOKUP_URL` and server-side `PATROLVIEW_API_TOKEN`.
* PATROLVIEW FIELD RULE: Event Ingress Time, Incident Number, Location Address, and primary 10-Code are all ordinary editable inputs after prefill. Prefill may set only fields the FTO has not changed; it never locks a field or overwrites an FTO correction. Manual entry remains available when the route is unavailable or returns no event.
* PARENT-RUN INHERITANCE: Dispatch values belong to the parent `TrainingRun`. Its Arrest Process, OVI Process, and continuation pages reference that same run rather than copying a second incident record; packet page IDs are derived deterministically from the run ID and supplement key. The Arrest Process supplement now carries the user-specified U-10.188 identifier in its form metadata.

## 3. VERSIONED CLEARANCE RULES & ACTIVITY TOTALS
Automatic clearance-derived counts apply only to new `clearanceRulesVersion: 1` runs that are complete and explicitly checklist-reviewed. Legacy runs retain their existing manual accounting and are not recounted.
* 1V: An explicitly selected Traffic Citations metric contributes one citation. Otherwise, a Traffic Stop or selected Solve Citation/Summons metric contributes one Solve Citation/Summons; other runs contribute one PremierOne Report. Distinct citation columns are not incremented together automatically.
* 2V: No automatic report or citation count.
* 3V: Transport starts unchecked on a new run. Selecting Arrest Made or 3V preselects transport and 3V. The FTO records the actual transport destination and destination type. If transport is cleared, the code changes to 1V; validation requires 1V for an arrest without transport and requires a destination for a transported arrest. A reviewed, complete 3V contributes one U-10.100, Prisoners Slated, PremierOne Report, Probable Cause Affidavit, and one Criminal Complaint per entered charge. These are local draft payloads, not filed or legally validated documents.
* 4V: Timeline evidence only; it adds no report/citation multiplier.
* Manual activity entries and eligible derived counts are combined for displayed totals. Editing a displayed total changes its manual portion; it cannot erase an eligible derived count. Run activity flags remain supporting evidence and do not duplicate clearance-derived totals.

## 4. CHECKLIST DEFICIENCIES & DAILY RATING PROJECTION
New run checklist items default to checked; duty checklist items are also treated as checked unless explicitly cleared. The FTO reviews and may edit the checklist. Applicable unchecked items create source-linked exceptions when deficiency automation is enabled; Limbo reports suppress rating projection.
* Exceptions are grouped by source run and target SEG category, so multiple failures in one category on one run use one articulation group with the source references. The FTO can edit the articulation and override the target category.
* For applicable, non-Limbo deficiencies, the daily category projection is UA unless an existing NRT is retained. Any Officer Safety category (18–24) with a deficiency is locked to UA for that report.
* Weekly/monthly summaries count reviewed, non-Limbo daily ratings. Do not describe this as an independent weekly performance score or claim a separate automatic weekly-A cap beyond the implemented category ceiling behavior. No numerical performance ratings are used.
* `W#D#P#` references identify the scheduled day and source packet page. Long narratives are represented by generated continuation pages; they are not separate persisted incident records.

## 5. FOUR-TAB MONTHLY WORKBOOK EXPORT
The monthly Excel output contains four distinct Sunday–Saturday weekly tabs, styled after the supplied U-10.174 reference and populated from local records. The 30 SEG rows sit above the Daily Activity Summary; text is protected against spreadsheet formula prefixes.
* Unused tabs remain present with zero counts. If the month or approved phase schedule requires more than four weekly ranges, export stops with an explanation; it never combines weeks or silently drops records. A selected record outside the four ranges also stops export.
* Monthly rating counts include reviewed daily summaries only and exclude Limbo days. Activity totals combine manual entries with eligible versioned clearance-derived counts. The export is local aggregation, not a live API or shared database view.

# Field Training Phase Timeline Notes

- Phase setup saves editable phase-week date ranges as consecutive Sunday–Saturday periods in the encrypted device workspace. Existing folders without ranges get defaults based on the current phase length.
- The verified standard schedule is 15 weeks: Phase I weeks 1–4 (4 weeks), Phase II weeks 5–8 (4 weeks), Phase III weeks 9–12 (4 weeks), and Phase IV weeks 13–15 (3 weeks). Workspace-root `src/config/phaseConfiguration.ts` is the single source for base phase durations and Limbo policy; the artifact-local config is a compatibility re-export. `model.ts` and `training-calendar.ts` derive phase lengths, week starts, and Limbo boundaries from it, and the local phase-setup Zod schema uses the same phase length for its minimum-range check. The monthly exporter consumes the saved/computed weekly ranges; default ranges are created from the registry, while approved extensions may lengthen them. The generated API schemas do not encode phase durations. Phase IV's fourth week is not enabled until the program duration is changed explicitly.
- FTO extension requests contain a target phase, extension type, requested week count, and unrestricted written justification. Requests are saved before success is shown; FTOs may continue paperwork while a request is pending.
- The FTO Coordinator reviews pending requests only after switching to the Coordinator role on the same device. Approval extends training weeks or extends the first Limbo period and moves later ranges. Denial removes the pending request. There is no cross-device sync, push notification, or server-side approval.
- Daily reports saved without a phase-week assignment while an extension is pending are assigned one after approval. Existing numbered reports remain snapshots.
- The monthly workbook has four weekly tabs and fails closed when the selected month or phase schedule requires more than four ranges. Separate weeks are never consolidated, and records are not silently omitted.

## Implementation Boundaries
- Clerk sign-in is present, but agency identity mapping, department role policy, and server-side authorization for training records are not configured. Role-specific screens are client-side workflow boundaries, not an agency authorization system.
- Training drafts and coordinator requests are stored in the device-local encrypted vault. They do not sync between devices or users; coordinator review must occur on the same device.
- No government dispatch feed is configured, no database-backed training-record API is connected to the portal views, and no external immutable audit-retention or SIEM service is configured.
- Do not alter the layouts or visual parameters of official printed forms U-10.173 through U-10.192 for phase timeline or extension changes.
