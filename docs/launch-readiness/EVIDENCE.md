## Isolated SQL installation and recovery rehearsal

`recovery-rehearsal.sh` creates a new local PostgreSQL 16.10 data directory under
ignored generated output, with an owner-only temporary Unix socket directory,
no TCP listener and an explicitly fictional database owner. Commands run with a
cleared environment and explicit host/user/database; no `DATABASE_URL`, `PG*`,
live credentials or configured application database are read or used. Its exit
trap stops that cluster; it does not stop application workflows.

Actual results:

1. Current `agency-training.sql` applied to the empty disposable database.
2. Inserted one fictional assignment, binding, packet and event. A second
   transaction inserted a packet/binding, then failed an audit event CHECK.
   Both second objects were absent after the connection rolled back.
3. A **separately supplied synthetic runtime grant set** allowed packet SELECT
   but not UPDATE, nor event DELETE/TRUNCATE. These permissions are not installed
   by the migration's comments and prove nothing about agency inherited grants.
4. Custom-format schema dump restored to a second database within this disposable
   cluster. Four table counts and saved narrative MD5 matched before/after.
   MD5 is only a fixture comparison, not a security signature.
5. The restored synthetic role still lacked packet UPDATE/event DELETE.

The timer reported 0 whole seconds for this tiny local backup/restore
(sub-second-resolution outcome), **not a usable RTO benchmark**. No encrypted
off-host backup, retention, service restart/failover, key recovery, legal-hold
restore, IdP integration, actual API concurrent transaction or agency disaster
recovery was tested. The fixture report is a synthetic SQL payload, not an
operationally valid completed daily report. Keep this distinction when using the
rehearsal as evidence.
